# 阶段 8：性能优化执行计划

## 1. 文档状态与目标

本文是 `实时DXR渲染器实施方案.md` 中阶段 8 的可执行细则，供实现者逐项开发、测试和提交。

- 目标硬件：NVIDIA RTX 4060 Laptop GPU。
- 输出目标：1920×1080，60 Hz。
- 默认内部渲染范围：1280×720 至 1920×1080，按 GPU 时间动态选择。
- 默认 GPU 预算：14.5 ms；硬验收线为 16.67 ms。
- 当前状态：8A–8E-2 的实现与既有 review 修复已完成；8B shared tile 因性能回退未采纳，8D AS 默认仍为 baseline，8F 因 1080p Path Trace 占比约 43.7% 未达到 45% 入口而不实施。8G 已实现并经 Codex review 修复 capture 退出 fence 和验收脚本，但旧 raw 证据不能完整通过正式口径：1080p fixed 回退超过 3%，默认 dynamic 实际为 720p，1800 秒运行没有动态切换，旧 AS capture 也没有加载 glTF。修复后的 3 秒 1080p forced-dynamic smoke 已通过；正式性能/capture/长时矩阵和人工/外部证据仍待完成，阶段 8 不得标记为完成。
- 前置条件：阶段 7 的渲染路径、历史资源、材质和 glTF 支持必须继续工作；阶段 7 尚缺的人工画质验收不能被阶段 8 的性能结果替代。

阶段 8 的核心不是盲目重写路径追踪器，而是依次完成：可信测量、低风险热点优化、资源生命周期重构、动态内部渲染分辨率，最后才根据数据决定是否试验 Inline Ray Query。

### 1.1 当前基线

以下数据来自阶段 7 的 Release Cornell 静态场景。它们是历史方向性基线：当时标题只显示最近一帧，且 `Total` 的时间戳不包含 AS 更新，不能直接作为阶段 8 的最终验收记录。

| 分辨率 | 当前 Total | AS | Path Trace | Temporal | À-Trous |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1280×720 | 10.87 ms | 0.00 ms | 5.25 ms | 1.73 ms | 3.70 ms |
| 1600×900 | 16.51 ms | 0.00 ms | 7.66 ms | 2.61 ms | 5.93 ms |
| 1920×1080 | 24.45 ms | 0.00 ms | 11.48 ms | 3.69 ms | 8.83 ms |

基线表明 Path Trace 和 À-Trous 都是主要 GPU 热点。原生 1080p 不能达到 60 FPS，但 720p 已有足够余量，因此本阶段的合理产品目标是“1080p 输出 + 动态内部渲染”，而不是在 RTX 4060 Laptop 上承诺 Cornell 原生 1080p 1 SPP 必定达到 60 FPS。

### 1.2 完成定义

只有以下条件全部满足，才能在主方案中把阶段 8 标记为完成：

1. Release、关闭 GPU Validation 时，1920×1080 输出的动态分辨率模式在 Cornell 场景连续运行 30 秒，三次运行的 GPU Total p95 都不超过 16.67 ms。
2. 默认动态模式内部尺寸不低于 1280×720，资源切换无每帧 CPU/GPU 强制同步，且不会持续抖动。
3. 固定 720p、900p、1080p 的 A/B 数据齐全；任何默认启用的优化均未造成超过本文阈值的性能或画质回退。
4. Debug + GPU-Based Validation 覆盖静态/动画模型、F1 调试视图、resize、最小化和恢复，未出现 D3D12 验证错误或设备移除。
5. 本进程本地显存占用低于 DXGI 报告预算的 70%，连续运行 30 分钟无持续增长。
6. 阶段 7 的视觉契约不退化。尤其是灯周围高方差区域，不允许因降采样、滤波器改写或错误历史复用而产生更强噪点、光晕、拖影或漏光。

## 2. 范围与非目标

### 2.1 本阶段包含

- 修正 GPU 时间范围，记录各 À-Trous 迭代，并提供滚动 p50/p95。
- 增加可重复的 benchmark 模式和 DXGI 显存预算遥测。
- 为 À-Trous 小步长迭代引入 Group Shared Memory，并保留基线路径作 A/B。
- 批量提交资源屏障，消除同一计算管线的重复绑定。
- 区分静态和动态 TLAS 构建标志，压缩静态 BLAS。
- 解耦输出分辨率和内部渲染分辨率。
- 用资源“代际”而不是全 GPU 等待来切换内部尺寸。
- 根据已完成的 GPU timestamp 样本控制内部渲染尺寸。
- 在严格数据门槛下评估 Inline Ray Query；仅评估，不预设采用。

### 2.2 本阶段不包含

- NRD、DLSS、Ray Reconstruction、Frame Generation 或 Reflex。
- ReSTIR、全新降噪器、神经网络降噪、采样器大改。
- Async Compute、多队列所有权转移或渲染图框架重写。
- 完整 Wavefront 队列、路径压缩、持久线程调度。
- 新的 glTF 功能、材质模型或灯光类型。
- 用动态分辨率掩盖现有画质缺陷。

如果实现某一优化必须引入以上非目标，应停止该工作包，在提交说明中记录原因，而不是扩大阶段范围。

## 3. 全阶段测量契约

### 3.1 GPU 时间范围

新增或调整统一样本结构，名称可按现有 Rust 风格微调：

```rust
struct GpuTimingSample {
    acceleration_structure_ms: f32,
    path_trace_ms: f32,
    temporal_ms: f32,
    atrous_ms: [f32; 4],
    tone_map_ms: f32,
    total_ms: f32,
    valid: bool,
}
```

时间戳必须满足：

- `Total` 从本帧 AS 构建/更新之前开始，到 ToneMap 完成后结束；不包含 `Present` 和等待垂直同步。
- AS、Path Trace、Temporal、四次 À-Trous、ToneMap 是 Total 的嵌套子区间。
- `sum(children)` 与 `Total` 的差值允许包含屏障和命令开销，但不能因为区间定义错误而长期大于 5%。
- 动态分辨率只消费 fence 已完成且 `valid == true` 的 GPU 样本，禁止用 CPU 帧时间或当前仍在执行的 timestamp。
- 窗口最小化、resize、shader reload、历史重置后的 warm-up 样本标记为无效。

### 3.2 统计和报告

- 使用固定容量环形缓冲，不在每帧分配内存。
- 至少保留最近 240 个有效样本；统计 p50、p95 和样本数。
- 排序可在低频报告时对固定缓冲的副本执行，不要每帧排序。
- benchmark 开始前预热 120 个有效帧；随后采样 30 秒。
- 每个配置独立运行三次，报告三次各自的 p50/p95，而不是把样本混在一起。
- 性能测试只使用 Release 且关闭 D3D12 Debug Layer/GPU Validation。Debug Validation 只用于正确性。
- 因当前程序使用 `Present(1)`，FPS 会受垂直同步封顶；性能判断以 GPU timestamp 为准。

建议命令行接口：

```text
--benchmark-seconds 30
--output-size 1600x900
--render-scale <0.50..1.00>
--dynamic-resolution
--target-gpu-ms <milliseconds>
--atrous-mode baseline|shared
--tracer-probe dxr|inline
```

`--benchmark-seconds` 结束时输出单行 JSON，至少包含 GPU 名称、输出尺寸、内部尺寸范围、模式、有效样本数、每个 pass 的 p50/p95、显存 usage/budget、历史重置次数和内部尺寸切换次数。JSON 字段名一经加入测试不得随意改变。

### 3.3 CPU 和命令记录指标

低频记录以下辅助指标：

- CPU 命令记录 p50/p95。
- 每帧 `ResourceBarrier` API 调用次数和 barrier 总数。
- 每帧 PSO/root signature/descriptor table 绑定次数。
- 非 Present 的 CPU fence 等待次数。
- 内部尺寸切换次数和原因。

它们用于证明优化确实降低了驱动/记录开销，不能替代 GPU 时间。

## 4. 目标架构和不可破坏的约束

### 4.1 输出尺寸与内部尺寸

引入明确类型，避免继续把 swapchain 尺寸当作所有资源的尺寸：

```rust
struct RenderExtent {
    width: u32,
    height: u32,
}

enum ResolutionMode {
    Fixed { scale: f32 },
    Dynamic {
        min_scale: f32,
        max_scale: f32,
        target_gpu_ms: f32,
    },
}
```

- `output_extent` 等于 swapchain client size。
- `render_extent` 用于 DXR、Temporal、À-Trous 及其历史资源。
- `display_output` 或等价 ToneMap 输出使用 `output_extent`，再复制到 swapchain。
- 内部尺寸按像素中心映射，并向 8 的倍数取整；不得超过输出尺寸，最小边不得为 0。
- 默认 1920×1080 输出的动态范围为 0.67–1.00，最小实际尺寸钳制到不低于约 1280×720。

F1 调试视图必须全部有定义：连续量（颜色、法线、深度等）可以做双线性显示；材质 ID、命中标志、拒绝 mask、history length 等离散量必须 point sample，禁止插值出不存在的 ID。

### 4.2 渲染资源代际

当前内部资源和 shader-visible heap 都与 swapchain 尺寸绑定。内部尺寸切换时，不能就地覆盖仍被 GPU 使用的 descriptor，也不能调用全局 `wait_for_gpu()`。建议引入：

```rust
struct RenderResourceGeneration {
    render_extent: RenderExtent,
    shader_heap: /* 当前 320 项同布局的独立 shader-visible heap */,
    frame_inputs: /* GBuffer/输出 */,
    histories: /* 双缓冲历史 */,
    ping_pong: /* À-Trous */,
    retire_fence: Option<u64>,
}
```

内部尺寸变化流程必须是：

1. 在 CPU 创建完整的新代资源和新的 shader-visible descriptor heap。
2. 复制或重写纹理、材质、几何等静态 descriptor；sampler heap 可以保持全局稳定。
3. 新代历史标记为无效并清零必要 metadata。
4. 在帧边界把 active generation 切到新代。
5. 记录旧代最后一次提交对应的 fence 值，将旧资源和旧 descriptor heap 一并放入退休队列。
6. 只有 `completed_fence >= retire_fence` 时才释放旧代。

允许在初始化、真正的 `ResizeBuffers`、shader hot reload 和关机时使用现有的全 GPU 等待；动态内部尺寸变化不得等待 GPU idle。

### 4.3 回退路径

每个影响 shader 算法或调度的大优化都必须有显式开关：

- `--atrous-mode baseline` 保留阶段 7 的全局纹理采样路径。
- `--render-scale 1.0` 恢复固定原生内部尺寸。
- Inline probe 永远不能悄悄替换默认 DXR 路径。

回退路径用于 A/B 和故障隔离，不要求永久暴露为最终用户 UI。

## 5. 工作包与建议提交

以下工作包按依赖顺序排列。Luna 可以在一个工作包内部拆分提交，但不要把多个尚未验收的工作包塞进同一个提交。每个提交必须能编译；涉及 shader 的提交还必须覆盖 `build.rs` 和 shader hot reload 列表。

### 8A：可信 GPU 基线和显存遥测

#### 实现任务

1. 把 Total 的起始 timestamp 移到 AS 更新之前。
2. 为四次 À-Trous dispatch 分别记录时间，同时保留聚合值。
3. 实现固定容量统计窗口及 p50/p95；为边界、空样本、NaN/无效样本写单元测试。
4. 增加 `--benchmark-seconds` 和单行 JSON 报告。
5. 设备创建时保留实际选中的 adapter，并取得 `IDXGIAdapter3`。
6. 每约 500 ms 调用一次 `QueryVideoMemoryInfo`，记录 local segment 的当前进程 usage 和 budget；不要每帧查询。
7. 窗口标题改成 Stage 8，低频显示最近有效 GPU Total、内部/输出尺寸和显存 usage/budget。标题不是正式报告来源。
8. 加入 PIX event 标签，至少覆盖 AS、PathTrace、Temporal、四次 À-Trous 和 ToneMap，方便抓取 GPU Capture。

#### 验收

- `Total >=` 任一子 pass，且与子 pass 总和差值合理。
- 静态 Cornell 的 AS 接近 0；动画模型能显示非零 AS update。
- benchmark 输出恰好一条可机器解析的 JSON，样本数与时长合理。
- 找不到 `IDXGIAdapter3` 时给出受控错误或 `N/A`，不能崩溃。
- 记录 720p、900p、1080p 三次新基线，并附在提交说明或阶段结果文档中。

建议提交：

```text
feat(stage8-profile): 建立可重复 GPU 基线和显存遥测
```

### 8B：À-Trous 小步长 Shared Tile

#### 设计

保持阶段 7 算法、权重、边缘条件和 root layout 不变，只优化 step 1 和 step 2。现有 `[numthreads(8, 8, 1)]` 每组 64 线程：

- step 1 的 5×5 kernel 最大 halo 为 2，所需 tile 为 12×12。
- step 2 的最大 halo 为 4，所需 tile 为 16×16。
- 为简化实现，两者都可按最大 16×16 tile 协作加载。

建议缓存以下 guide/signal：

| 数据 | 格式预算 | 16×16 大小 |
| --- | ---: | ---: |
| diffuse | `float4` | 4096 B |
| specular | `float4` | 4096 B |
| normal/roughness | `float4` | 4096 B |
| depth | `float` | 1024 B |
| hit | `float` | 1024 B |
| stable/material ID | `uint` | 1024 B |
| 合计 |  | 15360 B |

该预算低于 Shader Model 可用的 32 KiB groupshared 上限。线程以 stride 循环加载 tile，越界 texel 写明确 sentinel，然后执行 `GroupMemoryBarrierWithGroupSync()`；所有线程都必须到达 barrier，禁止在 barrier 前因越界提前 return。

step 4 和 step 8 继续使用基线全局采样路径。它们分别需要 24×24 和 40×40 tile；把全部 signal/guide 塞进 shared memory 会超过或逼近容量并损害 occupancy，不属于本工作包。

可新增 `stage8_atrous_shared.hlsl`，也可在现有 shader 中增加入口点，但必须同时更新 Release/Debug 编译和 hot reload。默认先保持 baseline，达到验收线后再把 shared 设为默认。

#### 验收

- baseline/shared 在固定随机种子、相同分辨率和足够历史帧下做截图差分。
- 非边缘稳定区域的输出应逐像素一致或仅有浮点重排带来的极小误差；边界不得出现黑边、wrap 或一像素错位。
- 720p、900p、1080p 中至少两个分辨率的聚合 À-Trous p50 提升不低于 15%。
- Total p95 不得回退超过 3%，灯边、几何边缘和运动画质不得肉眼退化。
- 如果未达到门槛，保留 baseline 为默认，记录实验结果，不继续为“完成任务”而扩大 shader 改写。

建议提交：

```text
perf(stage8-atrous): 缓存小步长滤波 tile
```

实施状态（2026-08-09）：shared tile 路径、A/B 开关、固定 benchmark 输出尺寸、Release/Debug 编译及 hot reload 已实现；RTX 4060 Laptop GPU 三档分辨率均发生明显性能回退，故未将其设为默认。实验数据见 9.2，下一工作包为 8C。

### 8C：屏障批处理和重复绑定清理

当前状态：代码实现和 RTX 4060 Laptop Release 数值 A/B 已完成；optimized 的 API/transition/bind 数值门槛通过，并已按项目决策切换为默认，`baseline` 永久保留为回退和 A/B 路径。截图/人工画面对比仍未完成，因此 8C 的画质验收债务和整个阶段 8 都不得标记完成。详细规格和验证记录见 [`阶段8C屏障批处理与绑定清理执行方案.md`](阶段8C屏障批处理与绑定清理执行方案.md)。

#### 实现任务

1. 为 `TrackedResource` 增加收集 transition 的接口，一次 `ResourceBarrier` 调用提交一组 barrier。
2. 优先批处理 history 集合、ping-pong、帧输入和输出之间同一边界的转换。
3. 同一帧四次 À-Trous 使用相同 PSO/root signature 时，只 bind 一次；每次迭代只更新确实变化的 descriptor table/constant。
4. 通过现有状态跟踪保证 before/after 正确，不要仅为减少调用数而依赖未经证明的 implicit promotion。
5. 本阶段不迁移 Enhanced Barriers；它会扩大改动面且不是当前瓶颈的必要条件。

#### 验收

- Debug GPU-Based Validation 无状态错误。
- 每帧 barrier API 调用数和重复 PSO/root signature 绑定数明显下降。
- CPU 命令记录 p95 提升至少 10%，或已低于 1.0 ms；GPU Total p95 不回退超过 3%。
- F1 视图、resize 和 shader reload 后资源状态仍正确。

建议提交：

```text
perf(stage8-d3d12): 批处理屏障和重复绑定
```

### 8D：静态 BLAS 压缩、TLAS 策略和预算记录

实施状态（2026-08-09）：代码、小模型 Release A/B、Debug GPU Validation 和首轮 Codex review 修复已完成；默认仍为 baseline。仓库没有能跨 committed allocation 粒度的代表性大 BLAS，compact-copy 分支、F1/resize/最小化人工矩阵和截图 diff 仍未验收，因此 8D 不能标记最终完成。实现、数据和未完成项见 [`阶段8D静态BLAS压缩与TLAS策略执行方案.md`](阶段8D静态BLAS压缩与TLAS策略执行方案.md) 与本文 9.4。

#### 实现任务

1. TLAS 是否允许 update 由真实需求决定：仅当 `animate_model` 且存在动画实例时使用 `ALLOW_UPDATE`；静态场景不要付出 update 的内存和 trace 代价。
2. 动态 TLAS 的初次 build 和后续 update 必须使用兼容的 build flags。
3. 静态 BLAS 使用 `PREFER_FAST_TRACE | ALLOW_COMPACTION`。
4. build 后通过 `EmitRaytracingAccelerationStructurePostbuildInfo` 取得 compacted size。
5. 在初始化的第二次提交中执行 compact copy；旧 BLAS 及 postbuild/readback 资源必须等相关 fence 完成后才释放。
6. 更新 TLAS instance descriptor，使其指向 compacted BLAS 的 GPU VA。
7. 记录每个 BLAS 及总计的 original/compacted bytes。不要对必须 update 的 TLAS 做压缩；静态 TLAS 是否压缩只有在 API 合法且实测有收益时才考虑。

#### 验收

- 静态场景 AS 每帧为 0；动画场景 update 正确且 p95 不高于 1.5 ms。
- compacted size 不大于 original size，TLAS 指针更新后画面与 baseline 一致。
- Debug Validation 无 AS build/copy/lifetime 错误。
- local memory usage/budget 比例低于 70%，结果写入 benchmark JSON。
- 如果某模型压缩收益过小，可以跳过 compact copy，但必须记录阈值和数据。

建议提交：

```text
perf(stage8-dxr): 压缩静态 BLAS 并区分 TLAS 策略
```

### 8E-1：解耦输出与内部渲染尺寸

这是动态分辨率的结构性前置，不与控制器一次实现。

实施状态（2026-08-09）：8E-1 代码已按方案分提交实现，8E-2 动态控制器和首轮 review 修复也已完成。已完成自动化检查、RTX 4060 Laptop Release 四档短时 smoke、两条 Debug + GPU-Based Validation、默认/强制动态矩阵和 50 次 fixed F2 生命周期验证；完整 F1/F2/resize/最小化/恢复/hot-reload 人工矩阵、确定性截图和无 resize 长时性能矩阵仍待 8G 验收，不能据此标记阶段 8 完成。

#### 实现任务

1. 引入第 4 节的 extent 和 resource generation。
2. 保持 swapchain/output 资源为 `output_extent`，重建所有路径追踪、Temporal、À-Trous 和历史资源为 `render_extent`。
3. ToneMap/显示阶段从内部最终信号采样并写满 output-sized `display_output`，使用像素中心双线性映射。
4. 为所有 F1 视图定义连续/离散采样规则。
5. 支持固定 `--render-scale`；未传参数时保持 1.0，确保行为向后兼容。
6. 内部尺寸切换创建新代并退休旧代，不等待 GPU idle。
7. 新代首帧强制 history reset，清除 rejection/history length 等需要初始化的资源。

#### 验收

- `--render-scale 1.0` 与阶段 7 固定原生输出一致。
- 0.67、0.75、0.83、1.0 均能稳定运行；降采样尺寸是合法的 8 倍数，1.0 必须精确保持原生输出尺寸（例如 1920×1080 不得变成 1920×1072）。
- 连续切换至少 50 次，完成 fence 后旧代数量回落，显存不持续增长。
- 内部切换期间非 Present fence wait 计数不增加。
- 11 个 F1 视图在内部尺寸不同于输出时均无越界、错位或 ID 插值。

| 参数 | 默认值 |
