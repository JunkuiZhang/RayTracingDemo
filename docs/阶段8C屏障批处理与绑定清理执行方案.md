## 2. 当前实现审计

### 2.1 Transition Barrier

当前 [`src/renderer/d3d12/resource.rs`](../src/renderer/d3d12/resource.rs) 中 `TrackedResource::transition` 每发现一次状态变化，就立即调用一次 `ID3D12GraphicsCommandList::ResourceBarrier`。因此同一个依赖边界上的连续 transition 没有作为数组批量提交：

- `transition_frame_inputs` 最多连续提交 9 次。
- `DenoiseHistory::transition_all` 最多连续提交 9 次。
- Temporal 前后分别切换 history、rejection mask 和帧输入。
- 四轮 À-Trous 在 ping/pong 之间逐资源切换，每次 diffuse/specular 各一次。
- ToneMap/Copy/Present 边界逐个切换 display output 和 back buffer。

以稳定 Cornell、`--atrous-mode baseline` 为例，实际 transition 数约为 58 个/帧，当前也对应约 58 次 `ResourceBarrier` API 调用。第一帧、resize、history reset 或动画路径的数量可能不同，因此必须以新增遥测为准，不能把 58 硬编码为运行时断言。

### 2.2 À-Trous Pipeline/Root Binding

当前 [`src/renderer/d3d12/pipeline.rs`](../src/renderer/d3d12/pipeline.rs) 的 `ComputePipeline::bind` 每次都执行：

1. `SetPipelineState`；
2. `SetComputeRootSignature`；
3. `SetComputeRootDescriptorTable`；
4. `SetComputeRoot32BitConstants`。

四轮 À-Trous 每轮调用一次完整 `bind`：

- `baseline` 模式的 PSO 序列为 baseline/baseline/baseline/baseline，理论上只需绑定一次 pipeline/root signature。
- `shared` 模式的 PSO 序列为 shared/shared/baseline/baseline，理论上只需绑定两次 pipeline/root signature。
- descriptor table 和 `[StepWidth, Iteration]` 每轮都变化，仍必须更新四次。

Temporal、ToneMap 和 DXR 使用不同 root layout 或不同管线，不在本工作包中跨 pass 合并绑定。

## 3. 范围与非目标

### 3.1 本工作包包含

- 可重复的 command-recording baseline/optimized A/B 开关。
- 传统 `D3D12_RESOURCE_BARRIER` transition 的同边界批量提交。
- À-Trous 连续相同 PSO/root signature 的重复绑定清理。
- CPU command recording p50/p95 及 API 调用计数遥测。
- benchmark JSON、CLI、单元测试、Debug Validation 和 RTX 4060 Laptop 真机 A/B。

### 3.2 明确不包含

- 不迁移 Enhanced Barriers，不引入 split barrier。
- 不删除必要的 UAV→SRV、SRV→UAV、Copy 或 Present transition。
- 不依赖 implicit promotion/decay，不把 tracked state 偷改成 `COMMON`。
- 不修改 HLSL、滤波公式、采样、root layout、descriptor heap 布局或资源格式。
- 不批处理 `raytracing.rs` 中 BLAS/TLAS build/update 的 UAV barrier；该部分属于 8D。
- 不重写 shader hot reload，不缓存跨帧或跨 command-list 的绑定状态。
- 不引入 render graph、第三方容器依赖或全局通用 D3D12 state cache。
- 不顺手实施 8D 的 AS 压缩或 8E 的动态分辨率。

## 4. A/B 模式和默认策略

新增实时参数：

```text
--command-recording-mode baseline|optimized
```

在 `src/realtime.rs` 增加：

```rust
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
pub enum CommandRecordingMode {
    #[default]
    Baseline,
    Optimized,
}
```

要求：

- `baseline`：同一批已收集的 transition 仍逐个调用 `ResourceBarrier`，À-Trous 每轮执行完整 pipeline/root bind，用作旧行为对照。
- `optimized`：同一依赖边界只调用一次 `ResourceBarrier`；À-Trous 仅在实际 pipeline 对象变化时重新绑定 pipeline/root signature。
- 两种模式必须走同一套 pass 顺序、同一套状态决策和同一套 descriptor/constants 更新，禁止复制两份完整 render loop。
- 初始实现阶段默认 `baseline`。只有第 10 节全部通过后，最终结果提交才可把默认改为 `optimized`；即使采纳，也永久保留 `baseline` 回退路径。
- CLI 帮助、未知值错误、缺失值错误、CPU reference 冲突检测和解析单元测试必须同步更新。
- 窗口标题低频显示 `Cmd baseline` 或 `Cmd optimized`，避免人工测试时混淆。

## 5. Transition Batch 设计

### 5.1 API 形态

在 `src/renderer/d3d12/resource.rs` 增加可复用 batch。命名允许调整，但职责必须等价：

```rust
pub struct TransitionBatch {
    barriers: Vec<D3D12_RESOURCE_BARRIER>,
}

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum BarrierSubmissionMode {
    Immediate,
    Batched,
}

#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
pub struct BarrierSubmitStats {
    pub api_calls: u32,
    pub transitions: u32,
}

impl TrackedResource {
    pub fn collect_transition(
        &mut self,
        batch: &mut TransitionBatch,
        new_state: D3D12_RESOURCE_STATES,
    );
}

impl TransitionBatch {
    pub fn submit(
        &mut self,
        command_list: &ID3D12GraphicsCommandList,
        mode: BarrierSubmissionMode,
    ) -> BarrierSubmitStats;
}
```

`BarrierSubmissionMode` 属于底层 resource 模块；renderer 在调用点把用户级 `CommandRecordingMode::Baseline/Optimized` 映射为 `Immediate/Batched`。不要让通用 resource helper 反向依赖 CLI/realtime 配置。

具体实现必须满足：

1. `state == new_state` 时不生成 barrier，也不增加 transition/API call 计数。
2. barrier 的 `StateBefore` 来自 `TrackedResource` 的真实 tracked state，`StateAfter` 为请求状态，subresource 继续使用 `D3D12_RESOURCE_BARRIER_ALL_SUBRESOURCES`。
3. `optimized` 对非空数组调用一次 `ResourceBarrier(&barriers)`；`baseline` 按原顺序对每个 barrier 单独调用一次。
4. 空 batch 禁止调用 `ResourceBarrier`。
5. 同一 batch 不允许同一 `TrackedResource` 出现两次；Debug 构建应断言或以等价方式防止矛盾的 before/after 链。
6. 收集顺序就是 API 数组顺序，不得排序，不得跨依赖边界移动。
7. Windows crate union 内的临时 `ID3D12Resource` COM clone 必须在 submit/clear/Drop 路径中恰好释放一次，禁止泄漏或 double-drop。
8. `submit` 后 batch 必须为空并可复用。为避免每帧重复分配，renderer 保留一个容量至少 32 的 scratch batch，或使用等价的可复用存储；不要每个边界新建 `Vec`。
9. `collect_transition` 与紧随其后的 `submit` 之间不得插入可能提前返回的 fallible 操作。tracked state 只能在确定生成 transition 时更新一次。
10. 原有单资源 `transition` 可以保留给初始化/低频路径，但每帧主 render loop 必须改走 batch；不要同时为同一资源发出旧 transition 和 batch transition。

### 5.2 不能省略的同步

À-Trous 相邻 dispatch 存在真实 producer→consumer 关系。ping/pong 的 UAV→`NON_PIXEL_SHADER_RESOURCE` transition 既改变状态也提供必要同步；下一目标的 SRV→UAV transition 同样必须保留。8C 只能把同一边界上的多个 barrier 放进一个 API 数组，不能删除它们或挪到下一次 Dispatch 之后。

Copy 前后也必须保持：

```text
ToneMap Dispatch
  → display_output: UAV → COPY_SOURCE
  → back_buffer: PRESENT → COPY_DEST
CopyResource
  → back_buffer: COPY_DEST → PRESENT
  → display_output: COPY_SOURCE → UAV
```

`GpuPass::Total` 的结束 timestamp 仍位于 display output 的 UAV→COPY_SOURCE transition 之后、back buffer 的 PRESENT→COPY_DEST transition 之前，与 8A 实现保持一致。不要为了少一次 API 调用把 back buffer transition 移进 Total；该边界必须拆成两个 submission。

## 6. 每帧批处理边界

按下表重构，每一行代表最多一次 optimized `ResourceBarrier` 调用。括号内是稳定 Cornell 的预期有效 transition 数，不是硬编码常量。

| 边界 | 收集内容 | 预期 transition | optimized 调用 |
| --- | --- | ---: | ---: |
| Path Trace 前 | 9 个 frame input → UAV | 9 | 1 |
| Path Trace 后 / Temporal 前 | 9 个 frame input → SRV；previous history → SRV；current history → UAV；rejection → UAV | 通常 19，首帧可更多 | 1 |
| Temporal 后 | current history → SRV；rejection → SRV | 10 | 1 |
| À-Trous 0 前 | ping diffuse/specular → UAV | 2 | 1 |
| A0 → A1 | ping → SRV；pong → UAV | 4 | 1 |
| A1 → A2 | pong → SRV；ping → UAV | 4 | 1 |
| A2 → A3 | ping → SRV；pong → UAV | 4 | 1 |
| A3 后 | pong → SRV | 2 | 1 |
| ToneMap 后 / Total 结束前 | display output → COPY_SOURCE | 1 | 1 |
| Total 结束后 / Copy 前 | back buffer → COPY_DEST | 1 | 1 |
| Copy 后 | back buffer → PRESENT；display output → UAV | 2 | 1 |

稳态目标是把 tracked transition API 调用从约 58 次/帧降到约 11 次/帧；考虑首帧或可选资源，正式验收使用 `optimized <= 12` 次/帧。实际 transition 数在 baseline/optimized 之间应完全相等；如果 optimized 通过减少 transition 数来达到目标，视为失败并重点检查同步是否被误删。

建议把现有 helper 改为“只收集，不提交”，例如：

- `DenoiseHistory::collect_transitions(batch, state)`；
- `collect_frame_input_transitions(batch, state)`；
- `collect_filter_pair_transitions(batch, ping_state, pong_state)`。

每个边界由 render loop 明确调用一次 `submit`，让依赖顺序在调用点可读。不要在 helper 内偷偷跨 Dispatch 累积。

## 7. À-Trous 重复绑定清理

### 7.1 ComputePipeline 接口拆分

将 `ComputePipeline::bind` 拆成等价的两个层次，同时可保留原 `bind` 作为便利包装：

```rust
pub fn bind_pipeline(&self, command_list: &ID3D12GraphicsCommandList);

pub fn set_arguments(
    &self,
    command_list: &ID3D12GraphicsCommandList,
    descriptor_table: D3D12_GPU_DESCRIPTOR_HANDLE,
    constants: &[u32],
);
```

- `bind_pipeline` 只调用 `SetPipelineState` 和 `SetComputeRootSignature`。
- `set_arguments` 只调用 descriptor table 和 root constants API，并继续检查 constant 数量。
- 原 `bind` 若保留，应严格等于先 `bind_pipeline` 再 `set_arguments`，供 Temporal/ToneMap 使用。

### 7.2 每帧局部绑定状态

不要在 renderer 中保存跨帧 state cache。command list `Reset` 后 root signature 初始为 undefined，每帧第一次 À-Trous Dispatch 前必须绑定。shader hot reload 会替换 pipeline 对象，跨帧缓存也容易引用旧对象。

optimized 模式仅在四轮 À-Trous 的局部作用域中按连续 pipeline run 分组：

```text
baseline mode: baseline × 4  → bind_pipeline 1 次，set_arguments 4 次
shared mode:   shared × 2 + baseline × 2 → bind_pipeline 2 次，set_arguments 4 次
```

可用 `std::ptr::eq` 比较当前 `&ComputePipeline` 与上一次引用，或用明确的 pipeline kind 枚举；不要比较名称字符串或 DXIL 字节。每次 pipeline/root signature 发生变化后，必须先绑定新 pipeline/root，再设置该轮完整 descriptor/constants，之后才能 Dispatch。

PIX event、timestamp query 和 barrier 不会替应用重置 compute pipeline/root state，因此它们之间不需要重复绑定。但 Temporal→À-Trous、À-Trous→ToneMap 仍使用各自完整 `bind`。

baseline command-recording 模式必须继续四轮完整 bind，以提供真实旧行为 A/B。

## 8. Command Recording 遥测

### 8.1 CPU 时间范围

新增 CPU command recording 统计，使用 `std::time::Instant`：

```text
开始：等待 frame fence 和收集旧 GPU timestamp 之后，紧邻 allocator/list Reset 之前
结束：ResolveQueryData 已录制且 command_list.Close() 成功之后
排除：wait_for_frame、ExecuteCommandLists、Present、fence Signal 和窗口事件等待
```

该范围包括 allocator/list Reset、AS update 命令录制、所有 pass、barrier、descriptor/root 更新、timestamp/PIX 命令和 Close。不要用 FPS、GPU timestamp 或整个 `render()` 墙钟时间替代。

benchmark 开始时清空 CPU histogram 和命令计数累加器。CPU 样本不经过三帧 GPU readback 延迟，应有自己的 `valid_samples`。建议复用 8A 固定内存 histogram 的百分位逻辑，禁止每帧排序或无界保存样本。

### 8.2 计数范围

每帧记录：

- `tracked_transition_api_calls`：本工作包 `TransitionBatch::submit` 实际调用 `ResourceBarrier` 的次数。
- `tracked_transition_barriers`：提交数组中的 transition 总数。
- `atrous_pipeline_binds`：四轮 À-Trous 实际调用 `bind_pipeline` 的次数。
- `atrous_argument_updates`：四轮 À-Trous 调用 `set_arguments` 的次数，应始终为 4。

计数不包含 `raytracing.rs` 内部 AS UAV barrier，也不把一个数组中的 N 个 barrier 误记成 N 次 API 调用。

### 8.3 JSON 契约

现有单行 JSON 增加稳定字段，推荐结构：

```json
{
  "command_recording": {
    "mode": "optimized",
    "cpu_ms": {
      "p50_ms": 0.42,
      "p95_ms": 0.61,
      "valid_samples": 7200
    },
    "tracked_transition_api_calls_mean": 10.0,
    "tracked_transition_barriers_mean": 58.0,
    "atrous_pipeline_binds_mean": 1.0,
    "atrous_argument_updates_mean": 4.0
  }
}
```

字段名一旦进入测试不得随意更改。均值分母使用 CPU command recording 的有效样本数；零样本输出 `null` 或项目现有 JSON 风格的明确值，禁止 NaN/Infinity。为 JSON serializer 测试补齐字段和值断言。

## 11. RTX 4060 Laptop A/B 矩阵

### 11.1 正式命令

关闭 Debug Layer/GPU Validation，使用 Release、插电和相同电源/驱动设置。每个组合运行三次 30 秒：

```powershell
target\release\ray_tracing_demo.exe --benchmark-seconds 30 --output-size 1280x720  --atrous-mode baseline --command-recording-mode baseline
target\release\ray_tracing_demo.exe --benchmark-seconds 30 --output-size 1280x720  --atrous-mode baseline --command-recording-mode optimized
target\release\ray_tracing_demo.exe --benchmark-seconds 30 --output-size 1600x900  --atrous-mode baseline --command-recording-mode baseline
target\release\ray_tracing_demo.exe --benchmark-seconds 30 --output-size 1600x900  --atrous-mode baseline --command-recording-mode optimized
target\release\ray_tracing_demo.exe --benchmark-seconds 30 --output-size 1920x1080 --atrous-mode baseline --command-recording-mode baseline
target\release\ray_tracing_demo.exe --benchmark-seconds 30 --output-size 1920x1080 --atrous-mode baseline --command-recording-mode optimized
```

每组取三次运行结果的中位数，记录：

- CPU command recording p50/p95。
- GPU Total p50/p95。
- AS、Path Trace、Temporal、À-Trous、ToneMap p50/p95。
- tracked transition API calls/barriers mean。
- À-Trous pipeline binds/argument updates mean。
- 有效 CPU/GPU 样本数、GPU 名称、PIX 状态和显存 usage/budget。

### 11.2 采纳门槛

以下条件必须全部满足：

1. 三个分辨率的 optimized tracked transition API calls mean 均不高于 12，且比 baseline 至少减少 70%。
2. baseline/optimized 的 tracked transition barriers mean 相同；À-Trous baseline 模式的 pipeline binds 从 4 降到 1，argument updates 保持 4。
3. 三个分辨率中至少两个的 CPU command recording p95 改善不低于 10%，或者 optimized 的三个 p95 都已低于 1.0 ms。
4. 任一分辨率的 GPU Total p95 不得回退超过 3%；其余 GPU pass 不应出现无法解释的显著回退。
5. Debug GPU Validation、F1、resize、最小化/恢复和 hot reload 全部通过。
6. 画面无变化；若截图工具可用，应 bit-identical。

如果 CPU 指标噪声较大，先检查插电状态、后台负载和样本数，再追加三次运行；禁止只挑最好的一次。若 API 调用下降但 CPU 已低于 1 ms，可按门槛采纳，但报告必须明确“调用开销降低，绝对 CPU 收益受计时分辨率/系统噪声限制”。

## 12. 失败和回退规则

- 任何 validation error、device removed、黑帧或 F1 数据错误：不得采纳，先修正确性。
- transition 数在 optimized 中减少：默认视为误删同步，逐边界核对，不得用画面“暂时正常”辩解。
- GPU Total p95 回退超过 3%：保持 baseline 默认，检查 barrier 是否被跨边界移动或产生多余同步。
- CPU 未达到门槛且仍高于 1 ms：保留 A/B 路径和数据，默认 baseline；不要扩大到 Enhanced Barriers 或 render graph 来“完成任务”。
- shared À-Trous 仍不是默认，不得用它的性能结果替代正式 baseline-À-Trous A/B。
- 若 Luna 无法在 RTX 4060 Laptop 上运行真机矩阵，只提交代码和自动测试，默认必须保持 baseline，并在交付报告中明确列出未运行项。

## 13. Review 清单

Codex review 将重点检查：

1. 是否真的一次 API 提交 barrier 数组，而不是仅把多次调用包进一个 helper。
2. 是否保留每个 producer→consumer、Copy 和 Present 边界。
3. tracked state、COM clone 和 batch clear/Drop 是否正确。
4. baseline/optimized 是否共享同一状态决策，避免两套 render loop 漂移。
5. command list Reset 后是否重新绑定 root signature；pipeline 改变后是否重设全部 root arguments。
6. descriptor table/constants 是否仍每轮更新。
7. hot reload 后是否可能复用旧 pipeline identity。
8. CPU 时间范围是否排除了 fence wait、Present 和事件等待。
9. JSON 计数是否记录 API 调用而非 barrier 元素数量。
10. 是否用三次运行中位数做默认决策，且文档没有夸大未执行的验证。

## 14. 官方依据

- Microsoft [`ID3D12GraphicsCommandList::ResourceBarrier`](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-resourcebarrier)：数组按给定顺序等价执行，并明确建议尽可能批量提交多个 transition。
- Microsoft [`Using Resource Barriers to Synchronize Resource States`](https://learn.microsoft.com/en-us/windows/win32/direct3d12/using-resource-barriers-to-synchronize-resource-states-in-direct3d-12)：资源状态由应用维护，连续 before/after 必须匹配。
- Microsoft [`Using a Root Signature`](https://learn.microsoft.com/en-us/windows/win32/direct3d12/using-a-root-signature)：command list 开始时 root signature 未定义；改变 root signature 会使旧 root arguments 失效；设置 PSO 不会自动设置 root signature。
- Microsoft [`Root Signatures Overview`](https://learn.microsoft.com/en-us/windows/win32/direct3d12/root-signatures-overview)：共享 root signature 的 PSO 可复用已绑定布局，并只更新发生变化的 root arguments。
